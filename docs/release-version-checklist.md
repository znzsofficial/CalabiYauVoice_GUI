# Release Version Checklist

This project currently stores the app release version in a few separate places. When preparing a new release, update all entries below in the same change.

**Default policy (user preference, 2026-11-06): keep routine releases lightweight.** Run checks appropriate to the changes, reuse passing results for unchanged code, and confirm the primary site's version and download availability. The extensive verification recorded for 2.1.26/2.1.27 is historical evidence, not the minimum for every release.

## Version Fields

- `androidApp/build.gradle.kts`
  - `defaultConfig.versionCode`: Android monotonically increasing integer, for example `30`.
  - `defaultConfig.versionName`: user-facing Android version, for example `"2.1.0"`.

- `desktopApp/build.gradle.kts`
  - `compose.desktop.application.nativeDistributions.packageVersion`: desktop package version, for example `"2.1.0"`.

- `androidApp/src/main/kotlin/com/nekolaska/calabiyau/feature/settings/AboutScreen.kt`
  - About page displays `PackageInfo.versionName` at runtime.
  - Keep its fallback version string in sync, for example `"2.1.0"`.

- `androidApp/src/main/kotlin/com/nekolaska/calabiyau/feature/settings/SettingsScreen.kt`
  - Fallback version string used if Android package info cannot be read.

## Update Metadata

- `downloadPage/downloads/latest.json`
  - `versionName`
  - `versionCode`
  - `changelog`
  - `publishedAt`
  - `apkUrl` / `apkSize`
  - `releases`: archive list served by the homepage. `webDist` uploads the APK to R2 (`calabiyau-releases/android/CalabiYauVoice-<version>.apk` plus `CalabiYauVoice-latest.apk`) and prepends the new version here. Keep older entries; do not delete 2.1.6.
  - `apkUrl` stays a same-origin path such as `/downloads/CalabiYauVoice-2.1.7.apk`. The Pages Worker streams the file from R2. Android `UpdateApi` does not need a code change.

- `downloadPage/dist/downloads/latest.json`
  - Generated by `webStatic`; do not hand-edit or commit `dist/`. The deployment tasks synchronize it from the source metadata.

## What Not To Edit

- Do not update dependency versions that only happen to match the app version, such as entries in `package-lock.json`, `yarn.lock`, `node_modules`, `build`, or `.git` logs.
- Do not edit generated Android build outputs under `androidApp/build`; they are regenerated by Gradle.

## Quick Search

Before finishing a release bump, search tracked source files for the old app version and old Android version code. Useful patterns:

```text
2.0.9
versionCode = 29
"versionCode": 29
packageVersion = "2.0.9"
versionName = "2.0.9"
Version 2.0.9
```

Adjust the old values to match the release you are replacing.

## Change-scoped checks

- Android code: relevant regression tests and compile/Lint as appropriate. `webDist` includes the final signed `assembleRelease`; a separate pre-release APK build and repeated compile are not mandatory.
- Shared or Desktop behavior/build changes: run the affected platform checks. A Desktop packageVersion-only bump does not require the entire Desktop suite or packaging.
- Website or Worker changes: run the relevant typecheck/tests. Android-only releases do not require search, balance and Worker suites merely because release metadata changes. `webPush` already builds the site and bundled Worker.
- Use normal incremental tasks. Do not default to `--rerun-tasks`, clean builds, live Wiki fetches, or repeated successful tests. Broaden checks when failures, new changes or a concrete unresolved concern justify it.
- Documentation-only closeout: `git diff --check` and review are sufficient; no app build or deployment.

## Default release sequence

1. Review all changes since the last release, including already committed work. Update the version fields and concise changelog **before webDist**; preserve historical versions, especially 2.1.6.
2. Complete the change-scoped checks above. Record what actually ran; optional fixture skips are not passes.
3. Commit source/version preparation, then run `.\gradlew.bat webDist`. It builds the signed release from that commit, updates the size/hash URL/archive record and uploads the two R2 objects. Confirm task success and final metadata's version and nonzero size; never deploy a preparation-time apkSize=0.
4. Commit generated metadata and push normally, then run `.\gradlew.bat webPush`. Confirm deployment succeeds to the production project/branch. Avoid a separate duplicate website build.
5. Check **the primary domain only** by default: `latest.json` has the expected version, notes and download URL; the versioned download responds successfully with the expected size (HEAD or one small Range request is enough). No mandatory full APK download, browser screenshot or historical-file sweep.
6. Record a short release summary, commits/deployment reference and checks. Fold known evidence into the metadata commit where practical; use at most one necessary documentation closeout commit, push it, and leave the tree clean.

## Extra verification only when relevant

- Signing key, signing configuration, build toolchain or installation issues: verify the package and certificate, comparing to a previous release when needed.
- APK upload, R2 binding, download Worker, cache or metadata-generation changes: verify the affected object/alias and full hash or Range behavior.
- Domain/CDN/routing changes or discrepancies: compare the affected domains and deployment URL.
- Archive handling changes: check the relevant historical download(s).
- User-requested full audit: run the explicitly requested expanded checks.

Do not make all extra checks a routine checklist. Existing release reports retain their original evidence; this policy governs future work.

Do not rebuild and silently replace a published version after generating its fingerprint: APK VCS metadata can change the bytes when Git HEAD changes, even if Kotlin source did not. If a rebuild is required, regenerate/upload/verify the corresponding metadata again rather than mixing artifacts.
